# PDF 阅读模块 · 设计方案 v1

> 目标：让本地服务支持对**参考文献 PDF** 划词提问，且**不改动也不影响现有的 HTML lesson 阅读**。
> 状态：待评审。评审通过后按第 9 节的阶段拆分实施。

---

## 0. 一句话方案

新增一条独立路由 `/pdf`，用 **pdf.js** 把 PDF 渲染成"画布 + 真实 DOM 文本层"，再通过一个**适配器**把现有划词组件的 4 个文档结构钩子接到 PDF 上。
HTML 阅读走原路径、用默认适配器，两条链路零交叉。

---

## 1. 目标与硬约束

| # | 要求 | 判定标准 |
|---|---|---|
| G1 | 能在浏览器里读参考文献 PDF 并划词提问 | 选一段 → 气泡四动作全部可用 |
| G2 | **不影响现有 HTML 阅读** | 9 个 lesson 页面行为逐项不变；`pdf.enabled=false` 时可完全回到当前状态 |
| G3 | 首页提供 PDF 入口 | `/` 目录页能看到文献分组并点进去 |
| G4 | PDF 的问答也进 `questions/` 归档 | 与 lesson 同一套回流闭环 |
| G5 | 模块化、可单独关闭 | PDF 相关代码集中在 3 个新文件里；删掉不影响 HTML 链路 |

**不做的事**（本版明确排除）：批注/高亮持久化、PDF 搜索、导出、扫描版 OCR、多 PDF 标签页。

**PDF 文件本身零改动**（重要澄清）：不转换、不重命名、不移动、不重排版。页面上看到的仍是 PDF 原版版式（图表、公式、上标引用全在），变的只是**谁来渲染它** —— 从浏览器内置阅读器换成页面内的 pdf.js。`参考文献/_txt/` 是**已经存在**的抽取结果，只作为"给 AI 的上下文"被读取，不参与显示。

## 2. 现状耦合点分析

改之前先看清现有的接头在哪 —— 模块切分必须切在这些缝上。

| 现有位置 | 现在做什么 | 对 PDF 的障碍 |
|---|---|---|
| `serveStatic()` | 静态服务，`.html` 走注入分支，其余直接流式返回 | PDF 需要的是"渲染页面"而不是字节流 |
| `injectAsk(html, lessonFile)` | 往 `</body>` 前塞 `window.__ASK__` + `ask-ai.js` | 只能作用于 HTML，对 PDF 二进制无意义 |
| `TOOL_ASSET_PREFIXES` | `['assets/ask-ai.js','assets/katex/']` 优先从工具目录取 | 需要新增 pdf.js 资源前缀 |
| `getLessonContext(rel)` | 强校验：在 `lessons/` 下、深度 ≤2、后缀必须 `.html` | PDF 在 `参考文献/` 下，后缀是 `.pdf` |
| `buildMessages()` | L1/L2/L3/L4 四层上下文，依赖 `lesson.text` / `lesson.sections` | PDF 没有 HTML，章节来自 outline，全文来自 `_txt/` |
| `getCatalog()` | 只扫 `lessons/**.html` | PDF 不在 lessons 下 |
| `indexPage()` | 按分类渲染课程列表 | 需要多一类"文献"分组 |
| `ask-ai.js` 的 `articleRoot()` / `currentSection()` / `enclosingBlock()` / `LESSON` | 假定文档是 HTML：查 `.wrap,article,main` 根节点、查 `h2` 判章节、向上找 `P/LI/TD` 当段落 | PDF 里这三个假设全部不成立 |

**结论**：障碍集中在"文档结构假设"这一处。把这 4 个假设抽象成**可替换的适配器**，其余全部复用 —— 这是整个设计的关键切入点。

## 3. 总体架构

```
                         ┌─────────────────────────────────────┐
   HTML lesson           │            ask-server.mjs           │        PDF 文献
   /lessons/**.html ────▶│  serveStatic → injectAsk            │
                         │                                     │
                         │  ┌──────────────┐  ┌─────────────┐  │
   /pdf?file=...  ──────▶│  │ 原路由(不动) │  │ /pdf 新路由 │◀─┼── pdf-reader.mjs
                         │  └──────────────┘  └─────────────┘  │   (新模块)
                         │                                     │
                         │  getDocContext(kind, rel)           │
                         │    ├─ lesson → getLessonContext     │
                         │    └─ pdf    → getPdfContext ───────┼── 读 _txt/ 全文
                         │                                     │
                         │  buildMessages: 按 kind 过滤目录    │
                         └──────────────┬──────────────────────┘
                                        │ /api/ask (docKind 缺省 lesson)
                     ┌──────────────────┴──────────────────┐
                     ▼                                     ▼
        ┌────────────────────────┐          ┌──────────────────────────────┐
        │  lesson 页面            │          │  /pdf viewer 页面             │
        │  ask-ai.js              │          │  assets/pdfjs/ (pdf.js 内核)  │
        │  + 默认适配器            │          │  assets/pdf-reader.js        │
        │                         │          │   └ 注册 PDF 适配器 ──┐       │
        └────────────────────────┘          │  ask-ai.js ◀─────────┘       │
                                            └──────────────────────────────┘
```

关键点：**两条链只在 `ask-ai.js` 的适配器接口处汇合，其余完全独立。**

## 5. 关键设计决策

### D1 · 路由：新增 `/pdf`，不改 `.pdf` 原路径 ✅

| 方案 | 评价 |
|---|---|
| 拦截所有 `.pdf` 请求改返回 viewer | ❌ 否掉。会改变"PDF 原文件可下载/可嵌入"的语义，且污染通用静态服务，回滚困难 |
| **新增 `/pdf?file=<相对工作区路径>`** | ✅ **采用**。与 HTML 链路物理隔离，可单独开关 |

原 `/参考文献/xxx.pdf` 保持返回真实字节流 —— 任何依赖原路径的地方（lesson 里的链接、外部工具）行为不变。

### D2 · 适配方式：全局适配器对象，而非注册回调 ✅

| 方案 | 评价 |
|---|---|
| 在 `ask-ai.js` 里写 `if (MODE === 'pdf')` 分支 | ❌ 否掉。1449 行的文件继续膨胀，每次改 PDF 都要冒碰坏 HTML 路径的风险 |
| `window.__askAI.registerAdapter(fn)` 显式注册 | ⚠️ 时序竞态：`ask-ai.js` 的 `boot()` 是异步的，注册调用可能晚于首次 `updateMeta()` |
| **`window.__ASK_ADAPTER__` 全局对象，boot 时读取一次** | ✅ **采用**。零接口面积、零竞态；代价仅是"脚本顺序有约束"，在文档和模板里写死即可 |

### D3 · 全文上下文来源：优先复用 `_txt/`，而非运行时解析 PDF ✅

| 方案 | 评价 |
|---|---|
| 每次请求用 pdfjs-dist 在 Node 侧解析 PDF | ❌ 主路径否掉。17MB 的 PDF 每次解析耗时高，且服务端要引入 pdf.js 的 Node 依赖 |
| **复用工作区已有的 `_txt/<同名>.txt`** | ✅ **采用**。7 篇全部已有，正文质量实测优秀（分页标记 `<<<PAGE N>>>` 可用来做页级切片） |
| 浏览器侧抽全文回传服务端 | ❌ 状态同步复杂，收益为零（`_txt` 已有） |

**文件名映射**：PDF 与 txt 名不完全一致（抽取工具截断过长文件名），用**双向前缀匹配**兜底：

| PDF | txt | 匹配方式 |
|---|---|---|
| `Active illumination Focus Variation.pdf` | 同名 `.txt` | 精确 ✅ |
| `Computational self-corrected quantitative 3D topographic imaging.pdf` | `Computational self-corrected quantitativ.txt` | 前缀 ✅ |
| `Three-dimensional imaging confocal profiler without in-plane scanning.pdf` | `Three-dimensional imaging confocal profi.txt` | 前缀 ✅ |

匹配失败 → 走降级（见第 8 节）。

### D4 · 章节：用 PDF outline，而非字号启发式 ✅

| 方案 | 评价 |
|---|---|
| 按文本层 span 的 `fontSize` 猜标题 | ❌ 脆弱：论文里图注、公式、表格字号都不规则 |
| **`pdf.getOutline()` 拿真实书签树** | ✅ **采用**。这是 PDF 自带的结构化信息，中文论文一般都有 |
| 没有 outline 时 | 降级为"第 N 页"（见第 8 节） |

outline 在**前端**取（viewer 里已经有 pdf.js 实例），服务端不碰 PDF 解析 —— 让 M1 保持零 PDF 解析依赖。

### D5 · 段落：按坐标聚合，分两阶段做 ⚠️

`enclosingBlock` 在 PDF 下拿不到 `<p>`，只能从文本层 items 的 `transform` 里反推。算法：

1. 取当前页 `getTextContent()` 的 items（每项带 x/y 与宽高）
2. 以选区 anchor 的 rect 为基准，取同 y 带（`|Δy| < 行高 × 0.6`）的 items 拼成"当前行"
3. 沿 y 向上下扩展：相邻行间距 `< 行高 × 1.8` 则并入，遇到大间距停止 → 成一个"段"
4. 拼接时按 x 排序

**阶段一先只做"当前页"**（`contextMode: "page"`）：成本低、鲁棒、对提问足够（一页约 2–4k 字，token 可控）。
**阶段二**再上坐标聚合的精确段落（`contextMode: "paragraph"`）。

⚠️ **双栏论文的坑**：左右栏 y 相同而 x 不同，朴素聚合会把两栏串成一行。需要先按 x 分布检测中缝、分栏处理 —— 所以刻意排到阶段二。

### D6 · 文档标识：统一 `getDocContext(kind, rel)` 入口 ✅

```
getDocContext('lesson', '论文导读/0005-literature-map.html') → 走原 getLessonContext
getDocContext('pdf',    '参考文献/Active illumination Focus Variation.pdf') → 走新 getPdfContext
```

`/api/ask` 请求体新增 `docKind` 字段，**缺省 `'lesson'`** → 现有前端请求行为完全不变（G2 的保障之一）。

`getPdfContext` 返回与 `getLessonContext` **同构**的对象：

```js
{ rel, category:'文献', title, heading, sections:[outline标题...], html:null, text:_txt正文, kind:'pdf', pageCount }
```

这样 `buildMessages()` 只需在"全文/章节"两处按 kind 分支，其余拼装逻辑一行不改。

### D7 · 目录分离：PDF 混入 catalog 但按 kind 过滤 ✅

| 方案 | 评价 |
|---|---|
| 单独维护一份 PDF 列表 | ❌ 首页要合并两个数据源，`/api/state` 要改两处 |
| **合并进 catalog，加 `kind` 字段** | ✅ **采用**。首页天然拿到入口，但必须同步做过滤：`buildMessages()` 里 **HTML 只列 HTML、PDF 只列 PDF** |

⚠️ 这条是 G2 的关键：如果不过滤，PDF 会出现在 lesson 的"课程目录"里，**污染现有 HTML 阅读的 L2 上下文**。实现时必须显式过滤并加断言。

### D8 · 渲染：按需渲染，不整篇预渲染 ✅

PDF 最大 18MB / 131 页。整篇渲染会卡死。

做法：先为每页建立**占位容器**（高度由首页 viewport × 页数算出，保证滚动条和总高度正确），用 `IntersectionObserver` 在进入视口 ±1 页时才真正渲染 canvas + textLayer。

### D9 · pdf.js 版本与许可 ✅

- 版本：**3.11.174**（最后一个提供 UMD 构建的稳定分支，与"零构建步骤"的项目哲学一致；已实测可用）
- 许可：Apache-2.0，可随工具分发
- 体积：`pdf.min.js` 320KB + `pdf.worker.min.js` 1.06MB
- 落位：`assets/pdfjs/`，并加入 `TOOL_ASSET_PREFIXES`

### D10 · `contextMode` 默认 `page`，而非 `full` ✅（附实测依据）

这一项原本是开放问题，实测数据出来之后结论已经明确 —— **`full` 不只是费 token，而是会给出错位的上下文**。

7 篇文献的实测规模（字符数取 `_txt` 实际长度，页数取分页标记 `<<<PAGE N>>>` 的个数）：

| 文献 | 全文字符 | 页数 | 字符/页 | full 模式实际会带上 |
|---|---:|---:|---:|---|
| Optical Measurement of Surface Topography | 593,882 | 333 | 1,783 | ⚠️ 截断到前 6 万 = **全书 10%**（约前 34 页） |
| 基于白光干涉术和变焦法的…（袁琳博士论文） | 112,840 | 131 | 861 | ⚠️ 截断到前 6 万 = **全书 53%**（约前 70 页） |
| 表面微/纳米计量中的光学测量方法综述 | 41,718 | 18 | 2,317 | ✅ 全文 |
| Computational self-corrected quantitative 3D… | 57,837 | 13 | 4,449 | ✅ 全文（接近上限） |
| (2019) 基于结构光照明的表面形貌测量系统 | 55,510 | 65 | 854 | ✅ 全文 |
| Active illumination Focus Variation | 26,729 | 11 | 2,429 | ✅ 全文 |
| Three-dimensional imaging confocal profiler… | 26,172 | 9 | 2,908 | ✅ 全文 |

**为什么 `full` 危险**：现有 `context.maxLessonChars: 60000` 会做前缀截断。读那本 333 页的书、翻到第 200 页时，AI 手里握着的却是**第 1–34 页**的内容 —— 它会自信地拿开头的基础概念去解释你正在看的章节。

**为什么 `page` 可行**：分页标记在 7 篇里**全部完整**（页数与 PDF 实际页数一一对应），所以按页切片是可靠的。每页 854–4,449 字符 ≈ 400–2,200 token，精确对应当前阅读位置。

**默认 `"page"`**，配置页可随时改成 `full` / `paragraph`。想再宽一点可以后续加 `pagePadding`（当前页 ±1 页，防跨页断句）。

## 6. 接口契约

### HTTP

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/pdf?file=<rel>` | 返回 viewer 页面（注入 `__PDF_DOC__` 与 `__ASK__`） |
| GET | `/api/pdf-list`（可选） | 列出可读 PDF；首页服务端渲染时用不到，留给前端刷新 |
| POST | `/api/ask` | 请求体新增 `docKind`（缺省 `lesson`）、`page`（PDF 页码） |

### 注入到 viewer 的全局

```js
window.__PDF_DOC__ = { docId, url, title, pages, hasText, outline }
window.__ASK__     = { token, lesson: docId, docKind: 'pdf', endpoint, exportUrl, title }
window.__ASK_ADAPTER__ = { docId(), root(), section(), block(range), page() }   // 由 pdf-reader.js 提供
```

### 配置项（`ask.config.json` → `pdf`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | `false` 时 `/pdf` 返回 404、catalog 不含 PDF、首页无入口 → 一键回到纯 HTML 状态 |
| `dirs` | `["参考文献"]` | 扫描哪些目录下的 `.pdf` |
| `textDir` | `"_txt"` | 全文抽取结果所在子目录 |
| `contextMode` | `"page"` | `full` / `page` / `paragraph`，控制 L4 粒度 |
| `categoryLabel` | `"文献"` | 首页分组名 |

## 7. 上下文层映射（PDF 模式下）

现有四层全部保留语义，不新增层：

| 层 | HTML 模式 | PDF 模式 |
|---|---|---|
| L1 | `MISSION.md`（分类优先） | 同（分类为"文献"，回退到工作区根 MISSION） |
| L2 | 本分类的 lesson 列表 | **只列 PDF**（不含 lesson，避免污染） |
| L3 | 课标题 + `h2` 章节列表 + 当前位置 | 文献标题 + **PDF outline 章节** + "第 N 页" |
| L4 | 整课正文 / 当前章节 | `_txt` 全文 / **当前页** / 聚合段落 |
| 局部 | 选中原文 + 所在段落 | 同（段落来自 D5 的坐标聚合结果） |

## 8. 降级与已知边界

| 情况 | 行为 |
|---|---|
| `_txt/` 里找不到对应全文 | 降级为"仅选区 + 当前页文本"（前端从 textLayer 抽），并在上下文里标注"未获得全文" |
| PDF 没有 outline | L3 章节降级为"第 N 页" |
| 扫描版 PDF（无文本层） | 前端检测 textLayer 为空 → 顶部提示"这是扫描件，无法划词"，不报错 |
| 超出 `maxLessonChars` | 沿用现有截断逻辑（前缀截断 + "…（已截断）"） |
| 中文 PDF 文本层定位偏移 | ⚠️ **实测已知问题**：pdf.js 用系统字体模拟 PDF 内嵌字体，宽度差异导致 span 与画布文字有像素级偏移，划词可能多选/漏选。缓解：补全官方 text-layer CSS、显式声明字体 fallback。列为阶段一必须复测项 |
| 超大 PDF（>50MB） | 前端仅按需渲染视口页，不整篇加载文本层 |

### P4 验收记录（2026-09-17 · 双栏调优）

**结论先行**：原来的 `blockOfRange` 在双栏论文上会**串栏**，而且还有一个更隐蔽的问题——
**段落会跨越标题/作者/单位这类视觉上分离的块**。两个问题都修了。

#### 排查过程

**第一步：先确认哪份 PDF 真是双栏。**
一开始我按"整页 x 分布直方图"判断，得出「袁琳综述是单栏」——**这个判断是错的**。
改成按**行**看才露馅：某一行在页面中部被切成 2 段，就是双栏。
（教训：用整体统计判断结构性特征，容易把信号平均掉。要看**局部**。）

**第二步：定位"没切开"的根因。** 把切分过程原样重放，打印每一行的分段情况：

```
y= 527  1 段: [11~89% 9个 内部最大间隙21px]  ⚠️ 左右栏没切开！
         «量方法主要包括共聚焦法、显微结构光照明法、中，实现超分辨»
```

**栏间间隙 21px，而切分阈值 22px** —— 差 1px 没切开。
根因：左栏每行的结尾位置都在变（实测右边界在 30%~49.5% 之间浮动），行末标点还会把
span 边界再往外撑。**用固定的"相邻 span 间隙 > 阈值"判断栏缝，本质上不可靠。**

#### 两处修改

**修改一：用全页列投影找中缝，而不是逐行看间隙。**
把页宽切成约 4px 的细桶统计覆盖率 —— 中缝是唯一一条**贯穿整页**的低覆盖带。
有了中缝位置，再按"span 中心在中缝哪一侧"分行，就稳定了。
同时要求空白带宽度 ≥ 页宽 1.5%，并把搜索范围收在 30%~70%（太靠边的是页边距，不是中缝）。

**修改二：同栏判定改成严格按中缝分侧。**

```js
// 错的：用 x 区间重叠判断同栏
return rr[0] < xHi + lineH * 2 && rr[1] > xLo - lineH * 2
// 对的：有中缝时严格分侧
return ((rr[0] + rr[1]) / 2 > gutterX) === anchorIsRight
```

原因：左栏行末右边界（409px）与右栏左边界（430px）只差 21px，而容差是 `lineH × 2 = 28px`
—— **左栏"够到"了右栏**，于是右栏段落里混进左栏内容（实测出现过）。

**附带修好的第三个问题：段落跨越视觉块。**
原来扩展阈值是固定的 `1.75 × 行高`，导致首页的标题/作者/单位被连成一段（选区 70 字 → 聚合 1245 字）。
改成**自适应行距**：先统计本页相邻行间距的**中位数**当"正常行距"，超过它 1.45 倍才算段落边界。
这样不同排版的文档都能自适应，也顺带解决了"跨栏跳变"（栏间的 y 跳变自然超过阈值）。

### P6 验收记录（2026-09-17 · 缩放网页后的画质）

**现象**（主人反馈）：在文献阅读页缩放网页比例后，PDF 内容变模糊。

**根因**：`canvas` 的像素尺寸是在**渲染那一刻**按当时的 `devicePixelRatio` 决定的
（`canvas.width = vp.width × dpr`），之后不会自己重画。网页缩放会改变 dpr，
浏览器只能把旧位图**拉伸**到新密度 —— 于是发虚。

```js
// 画的时候（一次性定格）
canvas.width = Math.floor(vp.width * dpr);   // dpr=1 时是 826
canvas.style.width = Math.floor(vp.width) + 'px';
// 网页缩放到 200% 后 dpr=2，但 canvas.width 还是 826
// → 826 个像素被铺到 826 CSS 像素上、再乘以 2 的设备像素 = 被拉伸，模糊
```

注意：**用页面自己的 `+` / `−` 缩放按钮不会模糊** —— 那条路径会 `layout()` 重建并重新渲染。
只有**浏览器层面的缩放**（Ctrl +/−、Ctrl 滚轮、触控板捏合）才有这个问题。

**修法**：把「画 canvas」抽成独立的 `paintCanvas(n, box)`，然后监听 dpr 变化并重画已渲染的页。

| 环节 | 做法 |
|---|---|
| 触发 | `resize` 事件为主 + `matchMedia('(resolution: Ndppx)')` 兜底（覆盖"视口没变但 dpr 变了"的情况，绑一次后用 `{once:true}` 重绑到新分辨率） |
| 防抖 | 220ms —— 连续缩放时只跑最后一次，不至于中间态反复重画 |
| 重画范围 | 只重画 `pageState[n] === 'done'` 的页；没渲染过的页滚到时自然会用新 dpr 渲染 |
| **文本层不动** | span 位置是 CSS 像素，与 dpr 无关，重建它反而会丢选区 |

**验证（7 项全通过）**

| 场景 | 结果 |
|---|---|
| 初始 | 像素宽 826 / CSS 宽 826 → 密度比 1 |
| 缩放到 200% | 像素宽 **1652** / CSS 宽 826 → 密度比 **2** ✅ |
| 再缩放到 150% | 密度比 **1.5** ✅ 连续跟随 |
| 还原 | 密度比回到 1 ✅ |
| 版面 | CSS 尺寸不变（826 → 826），不跳版 ✅ |
| 文本层 | 没有被重复创建（2 → 2）✅ |
| 划词 | 重画后仍正常 ✅ |

**测试时踩的一个坑**（值得记）：用 CDP 的 `Emulation.setDeviceMetricsOverride` **只改
`deviceScaleFactor`、不改视口尺寸**时，`resize` 和 `matchMedia` 都**不会触发**，
看起来像"修复无效"。但那不是真实缩放 —— 真实浏览器缩放会**同时**改变视口 CSS 宽度
（dpr 的变化正是由此而来）。把模拟改成「视口减半 + dpr 翻倍」后立刻通过。
**排查时先确认模拟是否等价于真实场景，别急着改实现。**

### P7 验收记录（2026-09-17 · 文献来源管理）

**需求**（主人提出）：首页的文献区加一个"添加文献"接口，支持**单篇添加**和**绑定目录**；
绑定的目录要能实时反映目录内的文献。

#### 数据模型：从「一个目录」扩展为「一组来源」

```json
"pdf": {
  "dirs": ["参考文献"],                    // 目录来源：里面的 PDF 会自动出现
  "files": ["D:/papers/某篇.pdf"],         // 单篇来源：可以指向工作区之外
  ...
}
```

| 设计点 | 做法 |
|---|---|
| 向后兼容 | `dirs` / `files` **都没配**时才回退到默认 `['参考文献']`；配了任一就按配置来 |
| 路径写法 | 同时支持「相对于工作区」和「绝对路径」（含 `D:/` 这种正斜杠写法） |
| **安全边界** | `/pdf?file=` 现在校验「文件必须落在某个已登记来源内」，否则 403 —— 否则这个接口就成了任意文件读取 |
| 实时性 | 每次 `scanPdfs()` 现扫目录，上层 catalog 只有 2 秒缓存，所以基本是即时的 |
| 缓存一致性 | 来源变更后清掉 `docIndexCache`，否则新加的文献不会进 `__DOC_LINKS__`（编号跳转就不认它） |

#### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/pdf-sources` | 当前 `dirs` / `files` / 已纳入的 `pdfs` + 工作区里可点选的 `candidates` |
| POST | `/api/pdf-sources` | `{ action: 'add-dir'\|'add-file'\|'remove-dir'\|'remove-file', path }` |

`candidates` 是扫一遍工作区得到的「含 PDF 的目录」和「所有 PDF」—— 让用户点选，不用手打路径。
（跑测试时它还真发现了我不知道的目录。）

#### 界面

首页文献分组的标题旁多了 `＋ 添加文献`，点开是管理面板：当前来源列表（可移除）+
绑定目录（输入框 + 候选 chips）+ 添加单篇（同）。添加后面板内会就地刷新首页的文献列表，
不整页重载。
